# 第 1 章：最小可用 Agent 与结构化 (Minimal Agent & Structured Output) —— 会思考的循环

## 1. 模块定位与核心目标

第 0 章结束时，我们拥有的只是一个「翻译机」：发一句话、收一段文本，无状态、无记忆、无行动力。本章把它升级为一个**最小可用 Agent**——能记住对话、能动手干活、且输出可被程序安全消费。

**核心目标：**

1. **Agent Loop（会话循环）**：在内存中保留对话历史，让模型进入「思考 → 行动 → 观察」的循环，直到它认为任务完成。
2. **Tools 路由（行动能力）**：定义 `Tool` trait 与 `ToolRegistry`，把「模型说想做什么」路由到「程序实际执行什么」。
3. **JSON Schema 约束（确定性基石）**：用结构化的 `ContentBlock` 与工具入参 schema 约束模型输出，确保每一层输出都能被 Rust 强类型系统（Serde）安全反序列化——这是后续所有状态机（Todo、Task Graph、Workflow）不崩溃的前提。

## 2. 架构决策与技术选型（Why we do this）

### 2.1 Agent Loop：为什么是「循环」而不是「一次调用」

单次调用无法完成任何需要外部信息的任务（「读一下 README」——模型没有眼睛）。ReAct 模式给出答案：让模型在**思考**（输出文本）与**行动**（输出工具调用）之间交替，程序负责执行工具并把结果**观察**（作为消息回填）给它。

循环的终止条件不是人工设定，而是模型自己声明：当响应不再包含工具调用（`finish_reason != "tool_call"`）时，模型认为任务完成。**「何时停止」本身成为了模型决策的一部分**——这是 Agent 与普通聊天机器人的本质分界。

### 2.2 对话历史即状态：`Message` + `ContentBlock`

第 0 章的 `Message.content` 是纯字符串；本章把它升级为**内容块序列**：

```rust
#[derive(Serialize, Deserialize, Clone, Debug)]
#[serde(tag = "type")]
pub enum ContentBlock {
    #[serde(rename = "text")]
    Text { text: String },
    #[serde(rename = "tool_call")]
    ToolCall { id: String, name: String, input: serde_json::Value },
    #[serde(rename = "tool_output")]
    ToolOutput { call_id: String, content: String },
}
```

为什么不是字符串拼接？因为**一条 assistant 消息可以同时包含文本和多个工具调用**，字符串会丢失这个结构。`ContentBlock` 请求响应共用一套类型（调用方构造 Text/ToolOutput，读取 ToolCall/Text），Serde 的 `tag = "type"` 保证与供应商线格式一一对应——这是 2.3 节「结构化约束」的第一层。

整个会话状态就是 `Vec<Message>`——一个纯内存的、每轮只追加的消息列表。**没有数据库、没有会话对象**：状态越简单，第 4 章做持久化时越容易替换存储层。

### 2.3 工具即数据：`ToolDefinition` 与 JSON Schema 约束

模型无法调用 Rust 函数，它只能**输出一段描述「我想调用什么、参数是什么」的 JSON**。因此工具对模型而言是三份数据（`ToolDefinition`）：

```rust
pub struct ToolDefinition {
    pub name: String,
    pub description: String,        // 告诉模型这个工具能干什么
    pub input_schema: Value,        // JSON Schema，告诉模型参数长什么样
}
```

`input_schema` 随请求发给供应商，模型据此生成合法的 `tool_call.input`。这是「结构化约束」的第二层：**模型输出不再是自由文本，而是受 schema 约束、可反序列化为强类型的 JSON**。后续章节的 `Action` 状态机（Todo 更新、Task Graph 变更）全部建立在这个保证之上。

### 2.4 工具路由：`Tool` trait + `ToolRegistry`

每个工具实现统一的异步 trait：

```rust
#[async_trait]
pub trait Tool: Send + Sync {
    fn name(&self) -> &str;
    fn description(&self) -> &str;
    fn input_schema(&self) -> Value;
    async fn execute(&self, ctx: &ToolContext<'_>, input: &Value) -> String;
}
```

`ToolRegistry` 用 `BTreeMap<String, Arc<dyn Tool>>` 存储：**排序确定**（发给模型的工具列表顺序稳定，降低响应抖动）、O(log n) 查找、`RwLock` 内部可变性（为第 7 章 MCP 运行时动态挂载工具预留）。路由本身只有一层：`dispatch(name, input)` 按 name 查表执行——本章没有权限、没有拦截器，那是第 2 章的事。

### 2.5 错误即消息：工具失败不是 Exception

工具执行出错（文件不存在、命令失败）时，**不 panic、不中断循环**，而是把错误文本作为 `ToolOutput` 回填给模型：

```rust
pub enum ToolResult {
    Output(String),                       // 执行成功（含工具自身的错误文本）
    NotFound { name: String, available: Vec<String> },  // 路由失败：未知工具
    Error(AgentError),                    // 执行层类型化错误
}
```

理由：绝大多数工具错误是**模型可以自行修正的**（路径写错了、参数缺了）——把错误喂回去，下一轮它自己会修。`NotFound` 还附上可用工具列表，模型甚至能从「工具名打错」中恢复。这是 Agent 韧性的第一课：**错误恢复的智能住在模型里，程序只负责如实汇报**。

## 3. 核心接口与数据流设计

### 3.1 主循环 `run_loop`（本章的心脏）

```rust
pub async fn run_loop(
    &self,
    messages: &mut Vec<Message>,
) -> Result<(), AgentError> {
    loop {
        let defs = self.registry.definitions();

        let response = self.client
            .stream_messages(&self.system, messages, &defs, MAX_TOKENS)
            .await;

        // 1. assistant 响应原样入历史（文本与 tool_call 块一并保留）
        messages.push(Message::assistant_content(response.content));

        // 2. 没有工具调用 → 模型宣告任务完成
        if response.finish_reason != "tool_call" {
            return Ok(());
        }

        // 3. 执行本轮全部工具调用，结果作为 user 消息回填
        for block in &response.content {
            if let ContentBlock::ToolCall { id, name, input } = block {
                let result = self.registry.dispatch(name, input).await;
                messages.push(Message::user_tool_output(
                    id.clone(),
                    result.as_content(),
                ));
            }
        }
    }
}
```

三段式循环：**追加响应 → 判定终止 → 执行工具回填**。每一轮 `messages` 都在增长，模型下一轮能看到自己上一轮调了什么、结果是什么——这就是「记忆」的全部实现。

### 3.2 一轮交互的完整数据流

```text
用户: "Read README.md and tell me what this project is about"
  │
  ▼
messages += [User: Text("Read README.md and...")]
  │
  ▼  stream_messages(system, messages, tools=[read_file, write_file, ...])
┌─────────────────────────────────────────────┐
│ Assistant: [ToolCall{id:"c1", name:"read_file",   │
│                       input:{"path":"README.md"}}] │
└─────────────────────────────────────────────┘
  │  messages += assistant 消息
  │  registry.dispatch("read_file", {"path":"README.md"})
  │      → Output("# bytemaker\n## 安装...")
  ▼
messages += [User: ToolOutput{call_id:"c1", content:"# bytemaker..."}]
  │
  ▼  下一轮 stream_messages（模型看到了文件内容）
┌─────────────────────────────────────────────┐
│ Assistant: [Text("bytemaker 是一个用 Rust ...")]    │
└─────────────────────────────────────────────┘
  │  finish_reason = "stop"（无工具调用）
  ▼
循环结束，控制权交还用户
```

### 3.3 首批工具集

本章注册最小而完备的一组内置工具，覆盖「读、写、改、查、跑」：

| 工具 | 职责 | 备注 |
| --- | --- | --- |
| `read_file` | 读文件（带行号前缀） | 模型的「眼睛」 |
| `write_file` | 写/建文件 | 第一个副作用工具 |
| `edit_file` | 精确字符串替换编辑 | 必须先 read 再 edit，模拟真实工作流 |
| `glob` | 文件名模式搜索 | 未知结构时的探索入口 |
| `command` | 执行 shell 命令 | 兜底能力；无任何防护（留给第 2 章） |

每个工具的 `execute` 返回 `String` 而非结构体——工具输出是给模型读的，字符串即通用格式；结构化留给工具**入参**（schema 约束）。

## 5. 演进预留 (What's Next)

1. **无执行边界**：本章 `command`、`write_file` 拥有无限权力，`dispatch` 拿到就执行。第 2 章在执行前插入 Permission 检查与 Hooks 拦截器（`ToolResult` 将增加 `Denied` 变体），本 trait 的 `check_permission` 钩子那时才被接线。
2. **无上下文管理**：`messages` 无限增长，迟早撑爆上下文窗口。第 3 章引入 Compact 与记忆检索。
3. **无循环上限**：本章 Lead 没有轮数限制（`max_turns = usize::MAX`）；第 8 章 subagent 复用同一 `run_loop` 时会带上限与 `MaxTurnsReached` 结果。
4. **可测性**：本章的循环测试依赖真实 API。第 5 章的 `CassetteProvider` 让 `run_loop` 的端到端测试离线确定性运行。

## 6. 验收标准 (Acceptance Criteria)

完成本章后，需通过以下验收：

1. **多轮工具循环端到端**：输入 README 示例 prompt `Read the file README.md and tell me what this project is about`，观察模型先发出 `read_file` 工具调用、收到文件内容后输出正确摘要——至少一轮「行动 → 观察 → 回答」完整发生。
2. **副作用链路**：输入 `Create a file called test.py that prints "hello", then read it back`，`test.py` 真实落盘且模型能读回并确认内容。
3. **结构化反序列化不崩溃**：工具调用的 `input` 能被 Serde 反序列化为强类型结构；构造一次畸形 JSON 输入，程序必须把错误文本回填给模型（而不是 panic），且下一轮模型能自行修正。
4. **路由失败自恢复**：构造一次幻觉工具名（如 `readfile`），断言收到 `NotFound` + 可用工具列表的回填消息，且会话能继续。
5. **会话状态保持**：完成第一个任务后追问 `What else can you do with it?`（不重复上下文），模型基于本会话历史作答，证明 `messages` 跨轮存活。
6. **离线循环测试**：用第 0 章的 `MockProvider` 扩展一个「脚本化」版本（第一次返回 ToolCall、第二次返回 Text），断言 `run_loop` 在零网络环境下走完两轮并正常终止——这是第 5 章盒带测试的雏形。
