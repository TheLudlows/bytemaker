# 第 4 章：持久化与异步状态机 (Persistence & Async State Machines) —— 生命周期管理

## 1. 模块定位与核心目标

前三章的 Agent 有一个共同前提：**一次只做一件事，进程退出即失忆，永远不会在未来醒来**。第 3 章的记忆解决的是「知识」跨会话；本章解决「**工作**」跨会话与跨时间——挂起的任务图、跑在后台的命令、定时唤醒的提示。

**核心目标：**

1. **Task Graph 持久化**：文件化的任务图（状态机 + `blocked_by` 依赖），跨会话存活，`create/list/get/claim/complete` 五操作。
2. **后台异步执行**：命令脱离主循环在后台跑（并发上限、超时、取消、进程树击杀），结果在后续轮回灌。
3. **Cron 定时唤醒**：5 字段 Vixie cron 调度 prompt，durable 落盘原子持久化，到点经交付队列注入主循环。
4. **`Send + Sync` 边界**：以上一切在 Rust async 里的落地代价——`tokio::spawn` 的 `'static` 约束如何反过来塑造架构。

## 2. 架构决策与技术选型（Why we do this）

### 2.1 Task Graph：文件即数据库

每任务一个 `.tasks/<id>.json`，无数据库。为什么不用 SQLite：**人可直接读、git 可追踪变更、零部署依赖**——任务图规模（几十个节点）远够用。与第 2 章 Todo（≤20 条、会话内工作记忆）形成两层分工：Todo 是「我现在打算干什么」，Task 是「跨会话的持久工作」。

路径安全完全复用第 2 章的沙箱哲学：`dunce` 规范化 + 词法 `path-clean` + 越界拒绝 + Unix 下拒绝符号链接的 `.tasks` 目录。

### 2.2 状态机与依赖：转换规则长在数据上

```rust
impl Task {
    pub fn can_claim(&self, incomplete_deps: &[String]) -> bool {
        self.status == TaskStatus::Pending && incomplete_deps.is_empty()
    }
    pub fn can_complete(&self, owner: &str) -> bool {
        self.status == TaskStatus::InProgress && self.owner.as_deref() == Some(owner)
    }
}
```

「能否领取」（依赖全完成）与「能否完成」（仅 owner 可完成）是 `Task` 的方法而不是散落在工具里的 if——**状态机的合法性约束集中在数据结构上**，任何调用方（工具、测试、第 8 章的 teammate）走同一套规则。依赖图（`blocked_by`）是数据不是代码：改计划 = 改文件。

### 2.3 后台执行：`tokio::spawn` 的类型系统逼出来的架构

`run_worker` 被 `tokio::spawn` 调度，其 `F: Future + Send + 'static` 约束直接决定了模块形态：

* **共享态必须 `Arc`**：worker 持 `BackgroundManager` 的克隆（内部 `Arc<Mutex<State>>`），注册表、就绪队列、取消信号全部走 Arc 共享——「Clone 是廉价的引用拷贝」是本模块的签名设计。
* **锁内不做 IO/await**：`start()` 的锁只覆盖「id 生成 + 插入」（顺手关掉并发 TOCTOU 窗口），文件写入在锁外——std `Mutex` 跨 await 是死锁教科书，粒度短才安全。
* **资源纪律**：并发上限 8（超出立刻报错而非排队）、120s 超时、50KB 输出截断、`kill_on_drop(true)` + 进程树击杀（杀 `cmd.exe` 不杀孙进程等于没杀）。

### 2.4 worker 的三路 `select!`：取消与超时是一等公民

```rust
let (status, exit_code, text) = tokio::select! {
    biased;
    _ = cancel.notified() => { /* TaskStop: kill_tree, Cancelled */ }
    _ = tokio::time::sleep(timeout) => { /* 超时: kill_tree, Failed */ }
    done = async { tokio::join!(child.wait(), drain(stdout), drain(stderr)) } => { /* 正常完成 */ }
};
```

`biased` 保证取消信号优先于一切——用户按停的语义永远不能被「刚好跑完了」竞争掉。三条路径都以 `kill_tree` + `finalize` 收尾，**任何出口都必须终结状态机**，否则任务永远 Running。

### 2.5 异步的本质：行动与观察解耦到不同轮次

后台命令返回的不是结果而是占位符（`[Background task bg_xxx started]`）。结果走两条路回灌：

* **被动**：`run_loop` 每轮顶部 `collect_and_inject`——就绪队列里的已完成任务以 user 消息注入，模型在**下一轮**才「看见」结果；
* **主动**：`TaskOutput` 工具可阻塞等待（带超时），模型明确要等时用。

主循环因此永远不被长命令阻塞——这是「async」在 Agent 语义层的含义：**一次行动的观察可以推迟到未来任意轮**。

### 2.6 Cron：调度器只生产，主循环才执行

tick 循环（60s 扫描）只做一件事：发现到点的任务，塞进 `delivery_queue`。**执行权永远在 `run_loop`**——每轮 `consume_queue` 排水，把到点的 prompt 作为 `[Scheduled]` user 消息注入。调度与执行的分离让 cron 子系统可以整体是「哑的」：无 LLM、无工具，只有时间判断。

交付语义是 **at-least-once**：消息入列后模型调用成功才 `acknowledge_jobs`；调用失败或用户取消则 `truncate` 历史 + `restore_jobs` 回滚重投——宁可重投不可丢任务。

### 2.7 durable：原子写与防御性加载

持久任务写 `.scheduled_tasks.json` 用 **temp + rename 原子替换**（进程崩在半写不会留下半个 JSON）。加载时逐条重新校验 cron 表达式/id/prompt，**坏的跳过而不是整体失败**——持久化文件可能被手改、被旧版本写入，加载器必须假设世界是脏的。

### 2.8 本章的 Rust 课：三种共享形态

| 模块 | 共享方式 | 为什么 |
| --- | --- | --- |
| `TaskStore` | 无锁、纯文件 | 操作天然串行（单 Lead），文件即真相 |
| `BackgroundManager` | `Arc<Mutex<State>>` | worker 与主循环并发读写注册表 |
| `CronManager` | `Arc<Mutex<State>>` | tick 循环与主循环并发 |
| （预告）`fs4` 文件锁 | 跨进程互斥 | 第 8 章多 teammate 进程抢同一 `.tasks/` |

加锁不是越少越好，而是**粒度与生命周期匹配**：进程内互斥用 `Mutex`，跨进程互斥才用文件锁——后者已在 `.tasks/.lock` 上预埋（`fs4`），是团队协作的前置投资。

## 3. 核心接口与数据流设计

### 3.1 run_loop 的生命周期接线（本章后的循环顶部）

```text
每轮模型调用前：
  ├─ bg_manager.collect_and_inject(messages)     # 后台完成结果回灌（Lead only）
  ├─ cron.consume_queue() → [Scheduled] 消息      # 到点任务注入（记 scheduled_start 快照）
  ├─ (teammate inbox 排水 — 第 8 章)
  ├─ compactor.prepare(...)                       # 第 3 章压缩
  └─ stream_messages(...)
模型调用成功：
  └─ cron.acknowledge_jobs(waiting_for_ack)       # 交付确认
模型调用失败/取消：
  └─ messages.truncate(scheduled_start) + cron.restore_jobs()   # 回滚重投
循环将退出时：
  └─ BackgroundStopHook（第 2 章挂的 Stop 钩子）：仍有运行中后台任务 → 注入提醒，拒绝退出
```

### 3.2 后台任务生命周期

```text
command 工具调用 (input 含 background:true)
  │
  ▼ start(): 锁内(id生成+插入+并发闸门) → tokio::spawn(run_worker)
占位符 tool_output: "[Background task bg_xxx started] ... TaskOutput 轮询 / TaskStop 取消"
  │
  ▼ worker: select! { cancel | timeout | 完成 } → kill_tree → finalize(状态+落盘 .log)
  │
  ▼ 就绪队列 ready: FIFO
  │
  ▼ 主循环下轮 collect_and_inject（或模型主动 TaskOutput 阻塞等待）
```

### 3.3 工具面

| 工具 | 职责 |
| --- | --- |
| `create_task` / `list_tasks` / `get_task` | 图的写与读（`blocked_by` 声明依赖） |
| `claim_task` / `complete_task` | 状态机转换（校验 `can_claim`/`can_complete`） |
| `command(background:true)` | 起后台任务 |
| `task_output` / `task_stop` | 轮询（可阻塞）/ 取消（kill_tree） |
| `schedule_cron` / `list_crons` / `cancel_cron` | cron 任务管理（`recurring`/`durable` 可选） |

## 5. 演进预留 (What's Next)

1. **cron 的已知债务**（模块注释自陈）：`start/shutdown_scheduler` 是 no-op、tick 循环句柄被丢弃（进程内无法停止调度）；`CronJob` 无 `#[serde(default)]`，旧文件缺一个字段会丢弃整个 durable 文件；`recurring` 任务在 `pending_delivery` 期间被跳过（系统睡眠后无 catch-up）；一处 `expect` panic 会毒化 mutex 并永久瘫痪子系统。
2. **后台任务是进程内的**：进程退出即丢（持久化刻意留给 task_system）——「重灾区」与「可丢失」的显式分工，但生产化需要恢复点语义（第 9 章崩溃一致性）。
3. **崩溃一致性不完整**：temp+rename 只覆盖 cron；task store 的单文件写非原子——统一 WAL/原子写是第 9 章议题。
4. **`worktree` 字段已预留**（`#[serde(default)]` 兼容旧 JSON）：第 8 章任务绑定独立 git worktree 时启用；`fs4` 文件锁同章用于跨 teammate 进程互斥。
5. **第 6 章 Workflow DAG** 构建在本章的任务图之上：节点即 Task，执行调度是本章状态机的编排化。

## 6. 验收标准 (Acceptance Criteria)

完成本章后，需通过以下验收：

1. **跨会话持久**：`create_task` 建任务 → 进程退出 → 重启 `list_tasks` 任务仍在且状态不变。
2. **依赖门禁**：`blocked_by` 指向未完成任务时 `claim_task` 被拒（错误回填列出未完成依赖）；依赖完成后可领取；非 owner 的 `complete_task` 被拒（`can_claim`/`can_complete` 语义有测试锁定）。
3. **并发上限与资源纪律**：第 9 个并发后台任务立刻报错（不排队）；120s 超时任务被击杀并标记 Failed；输出超 50KB 截断。
4. **取消语义**：`task_stop` 对运行中任务走 `kill_tree` 击杀并标记 Cancelled；`biased` select 保证取消优先于完成竞态。
5. **结果回灌**：后台任务完成后，下一轮 `collect_and_inject` 以 user 消息注入结果；`TaskOutput(block:true)` 能阻塞等待至完成或超时。
6. **Cron durable 闭环**：`schedule_cron(durable:true)` → 重启进程 → 任务加载并继续调度；非法 cron 表达式被拒；加载时坏条目跳过不炸整体。
7. **at-least-once 交付**：模型调用失败（如 PromptTooLong）时，已入列的 `[Scheduled]` 消息从历史回滚（truncate）并 `restore_jobs` 重投；成功调用后 `acknowledge` 清账。
8. **Stop 门禁**：存在运行中后台任务时，`BackgroundStopHook` 注入提醒并阻止循环退出。
9. **端到端**：`schedule_cron` 一条每分钟任务（prompt：列出当前目录文件）+ 起一个 `sleep` 后台命令，观察：后台命令先完成回灌、cron 到点注入新轮次、退出进程后 cron 任务仍在。
