# 第 2 章：工具链与安全沙箱 (Tools & Security Sandbox) —— 执行边界

## 1. 模块定位与核心目标

第 1 章结束时我们留了一个致命缺口：`dispatch` 拿到调用就执行——`command` 拥有无限权力，`write_file` 可以写磁盘上任何路径，而模型偶尔会「想错」。本章在模型与执行之间插入**执行边界**：干预（拦截危险调用）、审计（观测每次调用）、纪律（长任务的规划提醒）。

**核心目标：**

1. **Hooks 拦截器体系**：把扩展逻辑从循环体中剥离，在四个固定事件点触发回调，构建可插拔的中间件体系。
2. **Permission 三道闸门**：硬拒绝（不可绕过）→ 用户审批（交互确认）→ 工具自声明（按需审批），非交互环境一律 fail-closed。
3. **路径与命令的软沙箱**：文件工具的工作区边界检查、命令执行的时长/输出上限与编码兜底。
4. **Todo 队列**：用「状态约束 + 周期性提醒注入」给模型套上长任务的规划纪律。

**诚实声明**：本章的「沙箱」是**进程内软沙箱**——路径词法检查 + 命令正则黑名单 + 资源上限，不是操作系统级隔离（容器/microVM）。它防的是模型的**无心之失**，防不了蓄意逃逸；OS 级隔离属于第 9 章生产化的议题。

## 2. 架构决策与技术选型（Why we do this)

### 2.1 为什么是 Hooks 中间件，而不是在 `dispatch` 里加 if

最直觉的写法是在 `ToolRegistry::dispatch` 开头加权限判断——但权限只是众多横切关注点的第一个（还有输出体积告警、调用计数、提醒注入……）。把每种关切都塞进 dispatch，它很快会变成没人敢动的泥球。

Hook 体系的做法：**循环体只保留四个固定事件点，其余全部移入可插拔回调**：

| 事件点 | 时机 | 返回值语义 |
| --- | --- | --- |
| `UserPromptSubmit` | 用户提交输入后、LLM 调用前 | 无控制流影响（观测用） |
| `PreToolCall` | 工具执行前 | `Some(reason)` **阻断**，reason 成为 tool_output |
| `PostToolCall` | 工具执行后 | `Some(msg)` 作为**独立 user 消息**注入（不覆盖真实输出） |
| `Stop` | 循环即将退出时 | `Some(msg)` 注入并**强制继续**（拒绝退出） |

每个事件一个独立 trait（`PromptHook`/`PreToolHook`/`PostToolHook`/`StopHook`），回调是 `Box<dyn Trait>`——多一次堆分配，换来 hook 携带自有状态（如计数器）且能跨 async 边界。这套体系是全书的复用基座：第 5 章的轨迹采集、后台任务的结果注入，都从这里挂上去。

### 2.2 权限为什么是「三道闸门 + fail-closed」

`PermissionHook`（`PreToolCall` 上的内置 hook）把权限决策拆成串联的三道闸门：

```text
Gate 1  硬拒绝   DENY_PATTERNS 正则黑名单（rm -rf、sudo、shutdown、dd、chmod 777...）
                ↓ 不匹配
Gate 2  需审批   APPROVAL_PATTERNS（rm、curl|sh、eval、提权类）
                ↓ 命中 → Gate 3
Gate 3  问用户   IO::ask_permission 渲染 y/N 提示，读取用户决定
                ↓
Gate 4  自声明   registry.check_permission → 工具自己声明的
                PermissionCheck::NeedsApproval（如路径逃逸）也走 Gate 3
```

关键设计判断：

* **硬拒绝用正则而非子串匹配**——`\brm\s+-rf\s+/?` 防编码变形绕过（`rm  -rf /`、大小写混写）。黑名单永远是滞后的，但第一道闸门的意义是把「教科书级灾难」挡死在零成本层。
* **fail-closed**：非交互环境（测试、管道、无 stdin 的 teammate）里 `ask_permission` 返回 false → 拒绝。宁可误杀不可挂起——审批通道不存在时，默认答案是「不」。
* **拒绝不是 Exception，还是消息**：阻断的 reason（`"Permission denied: ..."`）以 `ToolResult::Denied` 回填为 tool_output——延续第 1 章「错误即消息」哲学，模型看到拒绝理由后能自行改道（换个安全命令、改个路径）。

### 2.3 路径沙箱：词法规范化 + canonicalize 混合

文件工具的边界检查（`safe_path_in`）分两层：

1. **词法层**：`path-clean` 归一化 `..`/`.`（不碰文件系统），快速判定是否逃逸工作区；
2. **物理层**：`dunce::canonicalize` 对比真实路径（剥掉 Windows `\\?\` 前缀、展开 8.3 短名、解析符号链接），防符号链接逃逸。

两条不变量：**不存在的路径也要能判**（`write_file` 建新文件不能被误拒——沿祖先目录 canonicalize 再拼回尾部）；**无法 canonicalize 时一律视为逃逸**（fail-closed）。`read_file`/`write_file`/`edit_file` 的 `check_permission` 用快速词法检查声明 `NeedsApproval`，把「路径看起来要出工作区」升级为用户决策。

### 2.4 命令执行边界：限时、限量、兜底解码

`command` 无法用路径逻辑约束，只能约束其**执行环境**：

* **30 秒超时**：`tokio::time::timeout` 包裹，防止模型跑出无限等待的命令；
* **50KB 输出截断**：在 UTF-8 字符边界上截断（否则 CJK 输出会在多字节序列中间 panic）；
* **编码兜底**：Windows 控制台在中文 locale 用 GBK（codepage 936），`encoding_rs` 先试 UTF-8 再试 GBK，避免输出变一片 U+FFFD。

这三条都是「防御性工程」而非「智能」——边界之内的问题交给模型，边界本身必须是笨而可靠的代码。

### 2.5 Todo 队列：行为约束靠提醒，不靠硬控

长任务里模型最常见的失败不是「做错」而是「漂」——做到第 5 步忘了第 2 步的目标。Todo 队列的解法分三层：

1. **状态机**：`TodoManager` 持有列表，硬不变量——**至多 20 条、至多 1 个 in_progress、status 必须合法**。模型提交的 JSON 违反任何一条，整个更新被拒绝（又是「错误即消息」）。
2. **工具**：`todo_write` 全量替换列表并渲染 `[/]/[>]/[x]` 视图；system prompt（第 1 章埋的）要求「多步任务先 todo_write 规划」。
3. **提醒注入**：`TodoReminderHook` 每累计 3 次非 todo 工具调用，注入一条 `<reminder>Update your todos.</reminder>`（`todo_write` 重置计数）。

为什么用提醒而不是强制？因为**计划的正确性只有模型自己知道**——程序无法判断「跳过第 3 步」是失误还是合理调整。约束状态格式（硬），提醒更新节奏（软），这是对「智能住在模型里」边界的又一次正确划线。

### 2.6 中间件的短路陷阱：注册顺序是不变量

`PostToolCall` 在**首个返回 `Some` 的回调处短路**。默认钩子组里 `SummaryHook`（计数，永远返回 `None`）必须注册在 `TodoReminderHook`（每 3 轮返回 `Some`）**之前**——否则提醒一旦触发，后续钩子被短路，调用计数丢失。这类「顺序即语义」的陷阱是中间件体系的固有代价，用注册函数处的注释 + 测试固定下来。

## 3. 核心接口与数据流设计

### 3.1 Hooks 注册表

```rust
pub struct Hooks {
    user_prompt: Vec<Box<dyn PromptHook>>,
    pre_tool:    Vec<Box<dyn PreToolHook>>,
    post_tool:   Vec<Box<dyn PostToolHook>>,
    stop:        Vec<Box<dyn StopHook>>,
}

impl Hooks {
    pub fn on_pre_tool<H: PreToolHook + 'static>(&mut self, h: H);
    pub async fn trigger_pre_tool(&self, registry: &ToolRegistry,
        ctx: &HookContext, name: &str, input: &Value) -> Option<String>;
    // 首个 Some(reason) 短路 → 循环据此返回 ToolResult::Denied
}
```

### 3.2 循环中的接线（run_loop 的第 2 章形态）

```rust
async fn execute_tool(&self, name: &str, input: &Value) -> ToolResult {
    let ctx = HookContext::new(Arc::clone(&self.io));
    // PreToolCall：权限闸门，Some(reason) → Denied（reason 回填给模型）
    if let Some(reason) = self.hooks.trigger_pre_tool(&self.registry, &ctx, name, input).await {
        return ToolResult::Denied { name: name.into(), reason };
    }
    let ctx = ToolContext { agent: self };
    self.registry.dispatch(name, &ctx, input, self.kind).await
}
```

`ToolResult` 在本章扩展出 `Denied` 变体——dispatch（未注册/受限）、pre_tool（被拒）、execute（出错）三层结果折叠进同一个枚举，`as_content()` 统一渲染为 tool_output 文本。

### 3.3 一条危险命令的完整路径

```text
模型: ToolCall{name:"command", input:{"command":"rm -rf /"}}
  │
  ▼ trigger_pre_tool
PermissionHook
  ├─ Gate 1: DENY_PATTERNS 命中 → Some("Permission denied: rm -rf / (destructive command)")
  │
  ▼
ToolResult::Denied → as_content() → ToolOutput 回填
  │
  ▼ 下一轮
模型看到拒绝理由 → 改用安全命令（如删单个文件走 Gate 2/3 审批）
```

### 3.4 默认钩子组

| Hook | 事件 | 职责 |
| --- | --- | --- |
| `ContextInjectHook` | PromptSubmit | 记录工作目录（观测） |
| `PermissionHook` | PreToolCall | 三道闸门权限管线 |
| `SummaryHook` | PostToolCall + Stop | 会话工具调用计数（累加器实现，防 compact 重写历史后丢计数） |
| `LargeOutputHook` | PostToolCall | 超大输出告警（>100K 字符） |
| `TodoReminderHook` | PostToolCall | 每 3 轮注入 todo 提醒 |

## 5. 演进预留 (What's Next)

1. **权限规则硬编码**：`DENY_PATTERNS`/`APPROVAL_PATTERNS` 是编译期常量，尚无「按项目/用户配置策略」的机制——策略外置属于第 9 章生产化。
2. **软沙箱的天花板**：进程内检查防不了蓄意逃逸（写脚本绕过、利用 canonicalize 竞态）；OS 级隔离（容器/microVM）在第 9 章。
3. **间接提示注入**：本章只管「模型想做什么」，不管「工具输出里藏了什么指令」——内容层防御同样归第 9 章安全议题。
4. **中间件复用**：第 5 章轨迹采集器将实现为 PostToolCall 中间件（零侵入观测）；第 4 章 `BackgroundStopHook`（后台任务收尾）也挂在本体系上。
5. **Todo 的持久化**：当前 Todo 仅存内存，会话结束即失；跨会话的任务管理由第 4 章 Task System 接管，Todo 退化为「单会话内的短期计划」。

## 6. 验收标准 (Acceptance Criteria)

完成本章后，需通过以下验收：

1. **硬拒绝零成本拦截**：`rm -rf /`、`sudo ...` 在 Gate 1 被拒，得到 `Permission denied: ...` 回填且不执行；正则防变形（`rm  -rf  /` 多空格、大小写）同样命中。
2. **审批交互闭环**：触发审批级命令（如 `rm foo`）时渲染 y/N 提示；用户拒绝 → `Permission denied by user`；**非交互环境（无 stdin）默认拒绝且不挂起**（有测试锁定此行为）。
3. **路径逃逸防御**：`read_file "../secret.txt"` 触发 `NeedsApproval`；`write_file` 写越界路径被 `safe_path_in` 拒绝；不存在的越界新路径同样拒绝（fail-closed）。
4. **命令执行边界**：超时命令（如 `sleep 60`）在 30 秒被杀并返回超时错误；>50KB 输出在 UTF-8 边界截断不 panic。
5. **Todo 不变量**：>20 条、双 `in_progress`、非法 status、空 content 四种输入全部被拒绝并回填错误文本；合法更新渲染出 `[/]/[>]/[x]` 视图。
6. **提醒注入语义**：连续 3 次非 todo 工具调用后注入 `<reminder>`；reminder 是**独立 user 消息**，不覆盖真实 tool_output（有测试锁定）；`todo_write` 重置计数。
7. **短路语义**：pre_tool 首个 `Some` 短路后续回调（有测试）；`SummaryHook` 先于 `TodoReminderHook` 注册的顺序不变量在 `build_hooks` 中以注释+代码固定。
8. **端到端行为**：README 示例 prompt #4（refactor 测试 TodoWrite 规划行为）与 #5（list + summary 测试 Hooks 全链路）跑通，观察规划-执行-提醒的完整循环。
