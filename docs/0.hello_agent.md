# 第 0 章：导览与环境 (Guide & Environment) —— 架构脚手架与 Hello, Agent

## 1. 模块定位与核心目标

本章是整个 `bytemaker` 项目的“地基”。进入复杂的 Agent 状态机和任务编排之前，必须先解决最底层的 I/O 问题：**如何让 Rust 核心逻辑与 LLM 供应商的 API 通信，又不让 SDK 类型侵入业务代码。**

**核心目标：**

1. **建立异步 I/O 基建**：初始化项目的目录结构、异步运行时与基础依赖体系。
2. **定义模型通信边界**：引入成熟的第三方 LLM SDK（如 `async-openai`）快速搭起基础设施，但**严禁 SDK 侵入业务逻辑**。通过接口防腐层（Adapter），由我们自己控制内外数据结构的转换。
3. **跑通最小调用**：从终端输入文本，无状态地获取 LLM 的完整响应，验证网络层与接口抽象这条路是否走通（Hello, Agent）。

## 2. 架构决策与技术选型（Why we do this）

### 2.1 异步运行时：选型 `tokio`

* **为什么**：LLM Agent 是网络 I/O 密集型系统，也包含部分 CPU 密集型任务（如向量运算）。`tokio` 的多线程异步调度器是 Rust 的事实标准。
* **设计约束**：整个 LLM 交互过程必须是非阻塞的 `async/await`，为第 4 章的并发 Task Graph 和第 7 章的 Actor 消息通信提供底层运行时。

### 2.2 LLM 通信边界：接口抽象与 SDK 封装 

* **为什么使用 SDK（如 `async-openai`）而不是手搓 HTTP 客户端？**
1. **快速收敛，聚焦核心**：第一天手搓底层 HTTP 请求、重试机制和复杂的协议字段映射，很容易陷入细节泥潭。用社区成熟 SDK 可以快速搞定基础协议通信，把精力集中到 Agent 本身的状态机和编排上。
2. **生态兼容性强**：`async-openai` 已经对 OpenAI 的标准接口做了完善的类型映射，同时兼容目前市面上绝大多数开源/国产模型（DeepSeek、vLLM 等），基本可以作为通用的通信层。

* **为什么必须“包装”一层（防腐层）？**
  避免供应商锁定（Vendor Lock-in）和类型污染。业务逻辑层（Agent Loop、Tools 路由）不能直接依赖第三方 SDK 的结构体。要把它映射成自己定义的 `Domain Message`，这样即使 SDK 出现破坏性更新、或者要彻底替换通信层，Agent 核心代码也不用改一行。

### 2.3 错误处理工程化：`thiserror` + `anyhow`

* **为什么**：生产级系统决不允许隐式 Panic。Agent 的韧性（如遇到 429 自动重试）依赖对底层错误的精确分类。
* **设计规范**：
* **底层（Providers）**：用 `thiserror` 定义强类型的领域错误 `LlmError`，负责把 SDK 抛出的第三方 Error（如 `OpenAIError`）转换并映射成内部错误枚举（如网络超时、Token 耗尽、鉴权失败等）。
* **顶层（应用入口）**：用 `anyhow::Result` 捕获并打印完整的错误上下文和调用栈，降低排错成本。

### 2.4 配置管理：`dotenvy` 与环境隔离

* **为什么**：遵循 12-Factor App 原则。密钥（如 `OPENAI_API_KEY`）和基础路由（如 `OPENAI_BASE_URL`）必须从环境变量或 `.env` 注入，保证生产部署安全。

## 3. 核心接口与数据流设计

本章的核心产出是建立模型层的依赖倒置（Dependency Inversion）体系。

### 3.1 核心领域模型 (Domain Models)

定义与特定厂商或 SDK 完全无关的通用对话结构。无论底层用什么 SDK，都必须在边界处做数据转换：

```rust
#[derive(Debug, Clone, PartialEq)]
pub enum Role {
    System,
    User,
    Assistant,
}

#[derive(Debug, Clone)]
pub struct Message {
    pub role: Role,
    pub content: String,
}

#[derive(Debug, Clone)]
pub struct CompletionResponse {
    pub content: String,
    pub prompt_tokens: u32,
    pub completion_tokens: u32,
}

```

### 3.2 抽象接口层 (The Interface Layer)

用 Rust 的原生异步 Trait（Rust 1.75+）定义抽象接口：

```rust
use std::future::Future;

/// LLM 供应商抽象接口
pub trait LlmProvider: Send + Sync {
    /// 发送无状态的消息列表，获取补全结果
    fn generate_completion(
        &self, 
        messages: &[Message],
    ) -> impl Future<Output = Result<CompletionResponse, LlmError>> + Send;
}

```

*设计意图：后续的 `Agent` 结构体只需要持有 `Box<dyn LlmProvider>`，彻底与具体的 SDK 调用解耦。*

## 4. 目录结构规划

项目初始的目录结构遵循领域驱动设计（DDD），明确层级边界：

```text
bytemaker/
├── Cargo.toml
├── .env.example             # 环境变量模板
└── src/
    ├── main.rs              # 启动入口、依赖注入 (DI) 与 CLI 
    ├── config.rs            # 配置加载模块 (Env, 参数读取)
    ├── error.rs             # 全局与领域错误类型定义 (LlmError)
    ├── domain/              # 核心业务模型
    │   ├── mod.rs
    │   └── message.rs       # Role, Message 结构体
    └── providers/           # 基础设施抽象层与 SDK 封装实现
        ├── mod.rs           # 定义 LlmProvider trait
        └── openai.rs        # 基于 async-openai 的 OpenAiProvider 实现

```

## 5. 演进预留 (What's Next)

本章用 SDK 跑通了**单次、无状态、纯文本**的 `Hello, Agent` 调用，搭好了核心骨架，也为下一步留了演进空间：

1. **状态缺失**：当前的 `generate_completion` 是阅后即焚的，第 1 章会引入 `Agent Loop`，在内存中保留并管理对话历史（Memory）。
2. **结构化缺失**：当前返回的是纯文本，第 1 章会借助 SDK 的 `response_format` 或 `tools` 参数，引入 JSON Schema，强制模型输出强类型的 `Action` 结构，作为 Agent 决策循环的引擎。

## 6. 验收标准 (Acceptance Criteria)

完成本章后，需通过以下验收：

1. **环境熔断**：未提供 `OPENAI_API_KEY` 环境变量时，进程启动阶段就抛出明确的配置加载错误并退出。
2. **异常捕获与透传**：模拟 API Key 错误或触发限流（429）时，必须正确捕获 SDK 抛出的异常，映射为 `LlmError::AuthError` 或 `LlmError::RateLimit` 透传给上层，不能触发隐式 Panic。
3. **接口解耦测试**：实现一个只打印日志并返回写死字符串的 `MockProvider`，证明入口代码（`main.rs`）能在不改一行核心逻辑的情况下自由切换 Provider。
4. **端到端跑通**：运行 `cargo run`，向 LLM 发送 "Hello, what system are you running on?"，在控制台打印出转换后的 `CompletionResponse`（包含文本内容与 Token 消耗统计）。
